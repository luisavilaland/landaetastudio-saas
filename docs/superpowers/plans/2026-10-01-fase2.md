## 3. TASK 0 — Spike: contrato real de MercadoPago ★ BLOQUEANTE

**Duración:** 0.5 día
**Depende de:** nada
**Bloquea:** T5

### Por qué existe

Cuatro supuestos del spec y del design **no son determinables desde la documentación**. MP se contradice en al menos un punto. Escribir el handler contra supuestos no verificados produce un sistema que parece funcionar en tests y no recibe ningún evento en producción.

### Alcance

| #   | Verificar                                                                                 | Fuente                               |
| --- | ----------------------------------------------------------------------------------------- | ------------------------------------ |
| 1   | Literales `type` + `action` de `subscription_preapproval`                                 | Preapproval real + webhook capturado |
| 2   | Literales `type` + `action` de `subscription_authorized_payment`                          | Cobro recurrente real                |
| 3   | `GET /authorized_payments/{id}` devuelve `external_reference`? `preapproval_id`? Ninguno? | Response real                        |
| 4   | `POST /preapproval` acepta `notification_url`? Llega el webhook?                          | Response + captura                   |
| 5   | `PUT /preapproval/{id}` acepta `notification_url`?                                        | Response de la llamada               |
| 6   | ¿La config por panel de MP funciona para Suscripciones? (su doc dice que no)              | Empirico                             |

### Procedimiento

```
1. Verificar MP_PLATFORM_ACCESS_TOKEN y MP_PLATFORM_WEBHOOK_SECRET en el entorno
2. Crear un preapproval real en la cuenta de plataforma (modo sandbox)
   - external_reference = <un tenantId de prueba>
   - back_url = <URL pública de test>
   - notification_url = <endpoint de test>          ← si el campo es rechazado, anotar
3. Completar el pago con tarjeta de prueba de MP
4. Registrar el webhook recibido: método, path, query params, headers, body crudo
5. Repetir para: cancelación, pausado, cambio de monto
6. Ejecutar GET /authorized_payments/{id} y GET /preapproval/{id} con el id recibido
7. Ejecutar PUT /preapproval/{id} con notification_url para ver si lo acepta
```

### 6.2 `calcProration({ precioActual, precioNuevo, currentPeriodEnd, now })`

Función **pura**. `now` inyectado (sin `Date.now()` interno).

```
crédito = (precioActual × díasRestantes / 30) - (precioNuevo × díasRestantes / 30)
díasRestantes = (currentPeriodEnd - now) en días
```

**Tests — tabla del transversal §5:**

| Caso                | Entrada                  | Esperado                                |
| ------------------- | ------------------------ | --------------------------------------- |
| Upgrade día 1       | 4000→8000, 30 días rest. | `direction: upgrade`, prorrateo ≈ -4000 |
| Upgrade día 15      | 4000→8000, 15 días rest. | ≈ -2000 (ejemplo textual del §5)        |
| Downgrade día 15    | 8000→4000, 15 días rest. | ≈ +2000, **sin** acreditar tiempo       |
| Período completo    | 30 días restantes        | prorrateo = 0                           |
| `díasRestantes` ≤ 0 | Período vencido          | No aplica → error de dominio            |
| Mismo plan          | mismo `planId`           | Rechazado en el endpoint, no aquí       |

**Regla:** devuelve topic, no decisión. `UNKNOWN` es una respuesta válida, no un error.

### 6.4 `resolveTenant(entityId, topic)` ★ (interfaz definida, implementación en T5)

Firma:

```ts
resolveTenant(
  entityId: string,
  topic: MpTopic,
  deps: { fetchPreapproval; fetchAuthorizedPayment }
): Promise<{ tenantId: string | null; strategy: 'local' | 'remote' | 'none' }>
```

**Estrategia L** (local, sin red):

```sql
SELECT tenantId FROM subscriptions WHERE "mpPreapprovalId" = $1
```

**Estrategia R** (remota): según `topic`.

- Trae `external_reference` → usar
- Trae `preapproval_id` → Estrategia L con ese id
- No trae ninguno → `{ tenantId: null, strategy: 'none' }`

**Tests:** los **3 resultados** del spike, replicados con `fetch` mockeado.

## 8. TASK 5 — Webhook de suscripciones

**Duración:** 2.5 días
**Depende de:** **T0**, T1, T2, T3
**Bloquea:** T6

### 8.1 Pipeline

Sigue design §6.2. 11 pasos. Puntos no obvios:

| Paso | Detalle                                                               |
| ---- | --------------------------------------------------------------------- |
| 4    | `dataId` del **query param** `data.id`, fallback al body              |
| 6    | `live_mode === false` + producción → `200` + `info`, no procesar      |
| 7    | `UNKNOWN` → `200` + `warn` con `{ type, action }`                     |
| 8    | `subscription_preapproval_plan` → `200` + `info` (fuera de alcance)   |
| 9    | `resolveTenant`; si `null` → `200` + `warn` con `{ entityId, topic }` |
| 11   | **Siempre `200`** salvo firma inválida (`401`)                        |

### 8.2 Transiciones — por convergencia, no por evento

Implementar el mapa de design §6.3. **No** `if (action === 'X') transicionar`.

Reglas transversales:

- `preapproval.authorized` + local `cancelled` → **SIN CAMBIO** (reactivar es explícito)
- `preapproval.paused` → `SIN CAMBIO` + `warn` (estado que el transversal no modela)
- `payment.rejected` + local `past_due` → **SIN CAMBIO** (no reinicia el día 0)
- `auto_recurring.transaction_amount ≠ plans.priceUyu` → `warn` con ambos, **no** ajustar `planId`

### 8.3 Idempotencia

| Tipo        | Mecanismo                                            |
| ----------- | ---------------------------------------------------- |
| Pago        | `lastProcessedPaymentId === paymentId` → no escribir |
| Pago        | Estado local ya es el objetivo → no escribir         |
| Preapproval | Convergencia: escribir solo si MP y DB difieren      |

### 8.4 Cliente MP

`mp-subscriptions.ts` (creado en T3) concentra `POST /preapproval`, `PUT /preapproval/{id}`, `GET /preapproval/{id}`, `GET /authorized_payments/{id}`.

| Regla        | Valor                                                               |
| ------------ | ------------------------------------------------------------------- |
| Timeout      | 15 s (30 s para `POST /preapproval` de T4)                          |
| `User-Agent` | `SaaS-eCommerce/1.0` (consistente con el webhook de órdenes)        |
| `429`        | Backoff acotado respetando `Retry-After`; si agota → `200` + `warn` |
| Error de red | `200` + `warn`. **Nunca** 5xx                                       |

### Criterios de aceptación

- [ ] `503` si falta `MP_PLATFORM_WEBHOOK_SECRET`
- [ ] `401` si falta `x-signature`, si la firma no valida, o si el timestamp expiró
- [ ] **Nunca** bypasea la firma en producción
- [ ] `data.id` del query param con fallback al body (test de ambos)
- [ ] `UNKNOWN` → `200` + `warn`, **cero escrituras** en DB
- [ ] `live_mode: false` en producción → no procesa
- [ ] Las **8 transiciones** de spec §2.5, cada una verificando estado **y** columnas
- [ ] Idempotencia: replay del mismo `paymentId` → 0 escrituras
- [ ] `subscription_preapproval` repetido → 1 sola escritura
